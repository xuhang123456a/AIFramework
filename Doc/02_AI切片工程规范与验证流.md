# AI 切片工程规范与验证流

> **核心结论（TL;DR）**：再好的架构原则，如果不落成死板的目录结构、机器可读的边界卡（`CONTRACT.md`）、脚手架脚本与编译守卫，AI Agent 在多轮迭代后依然会自行发明目录并跨界引用。本规范按 **方案 B（少数物理程序集 + Roslyn 编译守卫 + ArchTests 兜底）** 定义了 `AIFramework` 的标准仓库目录树、单个切片内部文件清单与 60 行 `CONTRACT.md` 模板、Luban 子表与自动生成 UI 视图接口的摆放规则，以及 **"脚手架建壳 → 读契约施工 → 编译守卫与无头单测验收"** 的全自动检验流。

## 一、 直观问题：为什么光有架构思想还不够

即便在项目规则里写明了"遵循垂直切片架构"，如果不对文件摆放、命名、依赖检查做机械化约束，AI 在连续开发三周后必然出现以下失控症状：

1. **目录结构漂移**：前天建的商店放在 `Features/Feature.Shop/`，今天 AI 新建活动时随手塞进 `Systems/Activity/Managers/`，甚至按技术类型拆回 `Controllers/`、`Models/` 水平分层。
2. **上下文阅读膨胀**：一个模块缺少简洁的入口边界说明，AI 每次改代码都要用全局搜索扫几十个文件，既浪费 Token，又容易把旧的坏写法当成先例抄进来。
3. **测试缺位或绑定引擎**：AI 改完逻辑只说"代码逻辑已自洽"，不写自动化验证用例；或者在测试里偷懒引用了引擎对象，导致无法脱离编辑器跑回归。

解决之道是把架构规则固化为**工程铁轨**：让 AI **没地方乱放文件、有明确的边界卡片可读、编译阶段就会被 Roslyn 分析器直接拦截**。

## 二、 标准仓库目录拓扑与命名规范（方案 B）

### 2.1 纯逻辑主仓与引擎挂载仓结构

工程采用 **方案 B（少数物理程序集 + Roslyn Analyzer 编译拦截）**，兼顾 Unity + HybridCLR 热更 DLL 极简粒度与纯 `.NET` 命令行毫秒级验证：

```text
AIFramework/
├── AGENTS.md                                 <-- AI 最高工程宪法
├── .gitignore                                <-- 忽略 bin/ obj/ .vs/ *.user 等构建与IDE临时文件
├── Directory.Build.props                     <-- 统一 LangVersion=9.0 / Nullable=enable / TreatWarningsAsErrors=true（放行 NU190x 与 CS8032）
├── Directory.Build.targets                   <-- 仅 netstandard 项目链接 build/IsExternalInit.cs（C# 9 record/init 垫片）
├── build/
│   └── IsExternalInit.cs
├── AIFramework.Pure.sln                      <-- 纯 .NET 主解决方案（日常开发与 dotnet test 主阵地）
├── artifacts/                                <-- 全部构建产物（bin/obj 统一落这里，避免污染 Unity 本地包导入）
├── Doc/                                      <-- 架构设计总纲、切片规范与搭建提示词
├── tools/
│   ├── new-slice.ps1                         <-- 一键生成标准切片目录、CONTRACT.md 与测试壳的脚本

│   ├── Assets/StreamingAssets/AIFrameworkDemo/ <-- Phase 1 的 12 字节夹具表（Phase 2 换 Luban）
│   ├── Packages/manifest.json                <-- 以 com.aiframework.* file: 本地包挂载纯逻辑程序集

│   ├── AIFramework.Analyzer/                 <-- Roslyn 编译守卫（netstandard2.0：AIF001~AIF004）

│   │   ├── AIFramework.Features.csproj
│   │   ├── Feature.DailySignIn/              <-- 命名空间 AIFramework.Features.DailySignIn
│   │   ├── Feature.HeroC_Shield/             <-- 命名空间 AIFramework.Features.HeroC_Shield
│   │   └── Interactions/                     <-- 显式双边特例隔离目录（Analyzer 白名单特许区）
│   └── Adapters/
```

> 本仓**不创建独立的 `AIFramework.Bootstrap` 程序集**：装配逻辑以 `ConsoleAppBootstrap`（Console 项目内）与 `UnityBootstrapper`（`Adapters.Unity` 内）的形式存在，避免热更 DLL 碎片化。上面的目录树中所有 `Feature.<Domain>` 按实际需求创建，不得为凑目录扫描结果建立空切片。
>
> 纯逻辑程序集**同时是 UPM 本地包**：包根放 `package.json` + `*.asmdef`（asmdef 必须 `noEngineReferences: true`），Unity 通过 `unity/Packages/manifest.json` 的 `file:` 路径直接编译同一份源码——零源码复制、零同步脚本。因此构建产物必须落在仓库根 `artifacts/`（`Directory.Build.props` 已统一重定向），`src/<Assembly>/` 下不允许出现 `bin/`、`obj/`，否则 Unity 会把编译产物当资源重复导入。

### 2.2 命名规范与目录红线

* **切片目录与命名空间一一锁定**：`AIFramework.Features/` 下的每个子目录必须命名为 `Feature.<DomainName>`（如 `Feature.Shop`、`Feature.DailySignIn`、`Feature.HeroC_Shield`），内部所有类的命名空间必须严格等于 `AIFramework.Features.<DomainName>`（或子命名空间）。`AIFramework.Analyzer` 正是依据 `AIFramework.Features.<DomainName>` 第二段命名空间标识来自动识别切片边界并拦截互引。
* **禁止跨目录散落**：属于同一特性的纯数据状态、Command/Event 处理逻辑、Luban 切片子表访问器、UI `Presenter` 逻辑大脑必须全部留在同一 `Feature.<DomainName>/` 目录内，禁止再按 `Managers/`、`UI/`、`Models/` 横向打散。
* **UI 生成物两侧分离**：工具生成的纯 C# 接口 `I<DomainName>View.g.cs` 放在当前切片目录（或 `Contracts` 指定生成区）；工具生成的 MonoBehaviour 挂载脚本 `<DomainName>ViewBinder.g.cs` 留在 `Adapters.Unity/Views/`。

## 三、 单一切片内部结构与 CONTRACT.md 边界卡

### 3.1 切片内部文件清单与体积上限

为确保 AI 能将单一切片的全部真相一次装进上下文窗口，规定单个标准切片内的源码文件**严格控制在 3~6 个核心文件**（单文件原则上不超过 300 行，超过则拆分为同目录内小步骤类）：

```text
src/AIFramework.Features/Feature.DailySignIn/
├── CONTRACT.md                     <-- 限 60 行以内：给 AI 读的边界卡与验收命令
├── SignInState.cs                  <-- 本切片专属纯数据状态（无方法，可序列化）
├── SignInTables.g.cs               <-- （若有独立子表）Luban 导出的本切片专属只读配置入口
├── SignInHandler.cs                <-- 接收 CQE 指令与事件的核心业务规则
├── SignIn.bindings.json            <-- （若带 UI）UI 绑定描述：控件语义名 + 类型，唯一可手改的 UI 契约源
├── ISignInView.g.cs                <-- （若带 UI）tools/viewgen 从 bindings.json 生成的纯 C# 视图接口（禁止手改）
└── SignInPresenter.cs              <-- （若带 UI）纯逻辑 UI 大脑，向 ISignInView 输出展示数据
```

*(注：若为强实时技能切片，则将 `SignInHandler.cs` 替换为实现固定管线阶段接口的 `<SkillName>Steps.cs`，并配套纯数据 `FrameData` 声明。)*

### 3.2 CONTRACT.md 标准模板（给 AI 看的唯一边界说明书）

每个切片根目录必须放置一份 `CONTRACT.md`，**严禁写成动辄几百行的长文档，严格限制在 60 行以内**。AI 接手任何重构任务时，第一动作就是先读这份卡片：

```markdown
# Feature.DailySignIn 切片边界契约

## 1. 职责定位
管理 7 日每日签到状态推进、补签校验与奖励发放请求；不含弹窗调度与背包存储实现。

## 2. 跨模块契约依赖（唯一合法入口）
* **订阅事件（In）**：`DayChangedEvent`
* **处理指令（In）**：`ClaimDailySignInCommand`、`RetroactiveSignInCommand`
* **只读查询（Out）**：`IPlayerLevelQuery`、`IInventoryQuery`（仅读补签卡数量）
* **独立子表（Config）**：`TbSignInReward`（通过 `IBinaryTableLoader` 加载本切片子表）
* **发出指令（Out）**：`GrantItemCommand`、`ConsumeItemCommand`
* **广播事件（Out）**：`DailySignInClaimedEvent`
* **UI 视图契约**：驱动 `ISignInView`（自动生成接口，勿手改）

## 3. 绝对禁区
* 禁止引用或 `using` 任何其他 `AIFramework.Features.*` 命名空间。
* 禁止直接扣减道具或读全局 `Tables` 单例，必须走 `ConsumeItemCommand` 与切片子表接口。
* 禁止引用 `UnityEngine`、协程或 `DateTime.Now`（时间必须通过 `ITimeProvider` 获取）。

## 4. 验收命令
dotnet test tests/AIFramework.Features.Tests/AIFramework.Features.Tests.csproj --filter "FullyQualifiedName~DailySignIn"
```

## 四、 跨切片交互与特例逃生阀规范

当业务开发遇到需要跨越当前切片边界的需求时，AI 必须按以下优先级选择方案，**禁止自行发明第 4 种捷径**：

1. **优先走 `Contracts` 既有 CQE / `GameplayTag`**：90% 的协作通过发标准 `Command`、听标准 `Event` 或配置通用 `GameplayTag` 即可解决。
2. **其次申请扩展 `Contracts` 协议**：若确实缺乏通用字段或接口（例如缺少一个 `OnBossShieldBrokenEvent`），AI 必须停下来先明确列出需要向 `AIFramework.Contracts` 追加的接口签名，由工程师确认后再动手实现。
3. **极少数双边专属特例走 `Interactions/`**：如果策划要求两个特定切片之间存在无法抽象为通用规则的专属联动，只允许在 `src/AIFramework.Features/Interactions/` 下新建单一独立文件（如 `Interaction_ShieldC_BoomerangD.cs`，命名空间为 `AIFramework.Features.Interactions`）。仅该命名空间在 `AIFramework.Analyzer` 中享有双边引用的显式白名单。

## 五、 AI 标准施工流与脚手架规则（SOP）

### 5.1 步骤一：严禁 AI 自建切片目录，必须用脚手架生成

当需要新增业务功能或技能时，禁止直接口头让 AI "自己建几个文件写一下"——因为 AI 容易拼错命名空间格式导致 `Analyzer` 漏检或忘建测试骨架。必须由脚本 `tools/new-slice.ps1 -Name DailySignIn -Type Meta` 一键生成：
* 标准切片目录 `src/AIFramework.Features/Feature.<Name>/` 及预设好正确命名空间的模板文件；
* 空白占位 `CONTRACT.md`；
* 对应的单元测试目录 `tests/AIFramework.Features.Tests/Feature.<Name>/`（已自动挂载 Mock CQE 总线、Mock `IBinaryTableLoader` 与 `MockTimeProvider`）。

### 5.2 步骤二：上下文最小化投喂

给 AI 派发任务时，只投喂与当前切片相关的最小文件集合（通常不超过 5~8 个文件）：
1. 全局规则：[AGENTS.md](../AGENTS.md)（自动加载）；
2. 相关契约：`src/AIFramework.Contracts/` 中本切片用到的 CQE 与视图接口（如 `I<Panel>View.g.cs`）；
3. 目标边界：`src/AIFramework.Features/Feature.<Name>/CONTRACT.md` 与该目录内现有代码；
4. 现有单测：`tests/AIFramework.Features.Tests/Feature.<Name>/`。

### 5.3 步骤三：Roslyn 编译守卫与架构依赖测试（双层拦截）

方案 B 依靠**"编译期实时拦截 + 提交前测试兜底"**两道防线确保 `AIFramework.Features` 单一大程序集内部不会演化出耦合泥潭：

1. **第一道防线：`AIFramework.Analyzer`（编译期 Error）**
   * 目标框架 `netstandard2.0`，同时挂接在 `.sln` 的 `.csproj` 与 Unity 的 `.asmdef`（标记 `RoslynAnalyzer` 标签）中，在敲代码和 `dotnet build` 时实时拦截：
     * **规则 `AIF001`**：`AIFramework.Features.<A>` 内禁止出现指向 `AIFramework.Features.<B>`（`A != B` 且非 `Interactions`）的任何符号引用或 `using` 指令；
     * **规则 `AIF002`**：纯逻辑程序集（`Contracts`、`Core`、`Kernels`、`Features`）内禁止出现 `UnityEngine`、`UnityEditor`、`Godot` 命名空间引用；
     * **规则 `AIF003`**：所有挂载 Analyzer 的纯逻辑程序集（`Contracts`、`Core`、`Kernels`、`Features`，由 `context.Compilation.AssemblyName` 白名单判定，不得靠命名空间前缀猜测）内禁止调用非确定性系统 API（`DateTime.Now`、`DateTime.UtcNow`、无参 `new System.Random()`）；
     * **规则 `AIF004`**：`AIFramework.Features` 内禁止引用或 `using` `AIFramework.Core`、`AIFramework.Kernel.Turn`、`AIFramework.Kernel.Realtime` 或 `Adapters.*`（切片只能依赖 `AIFramework.Contracts` 接口）。

### 多玩法卡带一览（同一个内核承载多种规则）

`GameplayKernelType` 是"卡带槽位"，不是"引擎类型"：同一内核可以装多套内容，装配层按枚举创建对应会话。

| 卡带 | 内核 | 输入端口 | 只读视图 | 场景 |
|---|---|---|---|---|
| `Turn` | Kernel.Turn | `TurnWorld.Enqueue` | 无（最小演示） | `DemoScene` |
| `CardBattle` | Kernel.Turn | `ICardBattleInput`（出牌/结束回合） | `ICardBattleReadView` | `CardBattleScene` |
| `Match3` | Kernel.Turn | `IMatch3Input`（交换两格） | `IMatch3ReadView` | `Match3Scene` |
| `Realtime` | Kernel.Realtime | `IIntentWriter` + `IRealtimeSandbox` | `IUnitWorldReadView`/`IProjectileWorldReadView` | `DemoScene` |

纪律：新增玩法优先扩"视图/输入端口 + 新卡带值"，**不得**让适配层引用内核具体类型；UI 只认端口接口。
2. **第二道防线：`AIFramework.ArchTests`（单元测试兜底）**
   * 包含对 `AIFramework.Analyzer` 的**负向编译回归用例**（用 `CSharpCompilation` 构造违规代码片段，断言编译器必须抛出 `AIF001`~`AIF004`）；
   * 结合 `NetArchTest.Rules` 扫描所有编译后程序集，确保 `Contracts` 零内部依赖、`Core`/`Kernels`/`Features` 各自仅单向依赖 `Contracts`，并校验每个 `Feature.*` 目录下必须存在且不超过 60 行的 `CONTRACT.md`。
   * **路径定位规则**：测试严禁依赖 `Environment.CurrentDirectory`（`dotnet test` 工作目录位于 `bin/` 下）。统一用 `[CallerFilePath]` 在编译期注入源文件绝对路径回溯仓根（如从 `tests/AIFramework.ArchTests/` 下的文件向上两级）；目录扫描只遍历真实存在的 `Feature.*`，跳过 `Interactions/`，且**目录缺失时断言失败而非静默跳过**。

```csharp
private static string RepoRoot([CallerFilePath] string callerFile = "")
    => Path.GetFullPath(Path.Combine(Path.GetDirectoryName(callerFile)!, "..", ".."));
```

## 六、 实战演练：新建一个 Feature.DailySignIn 切片的可检验验收标准

以在商业框架中新增"7 日每日签到"功能为例，检验整套规范是否真正跑通：

1. **脚手架创建与编辑**
   * 执行 `pwsh tools/new-slice.ps1 -Name DailySignIn -Type Meta` 生成目录与测试模板。
   * 填写 `CONTRACT.md` 契约，AI 仅在该目录与对应测试目录内编写 `SignInState`、`SignInHandler`（处理重复领取防重、跨天刷新、补签扣代币请求）与 `SignInPresenter`（面向自动生成的 `ISignInView` 输出 7 格状态）。
2. **必测边界用例（写入 `Feature.DailySignIn` 测试类）**
   * **正常链路**：第 1 天发送 `ClaimDailySignInCommand`，断言向总线发出 1 条 `GrantItemCommand`，状态变为已领，Presenter 刷出第 1 格为 `Claimed`。
   * **重复提交反例**：同一天连续发送两次 `ClaimDailySignInCommand`，断言第二次被拒绝，仅触发 1 次发奖指令。
   * **跨天重置与周期边界反例**：通过 `MockTimeProvider` 将时间推进 24 小时后断言第 2 格解锁；未领满 7 天前不提前重置周期。
   * **余额不足补签反例**：`MockInventoryQuery` 返回补签卡数量为 0 时发起 `RetroactiveSignInCommand`，断言不发送 `GrantItemCommand` 且状态不变。
3. **最终验收命令与合格标准**
   * 在终端依次执行：
     ```powershell
     dotnet test tests/AIFramework.Features.Tests/AIFramework.Features.Tests.csproj --filter "FullyQualifiedName~DailySignIn"
     dotnet test tests/AIFramework.ArchTests/AIFramework.ArchTests.csproj
     ```
   * **交付判定**：上述两条命令全部返回退出码 `0`（All Tests Passed），且 `git status` 检查变更文件严格局限于 `Feature.DailySignIn/`、`tests/AIFramework.Features.Tests/Feature.DailySignIn/` 以及经确认的新增 `Contracts` 协议文件（如有），即视为合格交付。

## 六之三、 五层验证流水线（当前仓库实际执行的顺序）

本仓已从"只有 dotnet test"演进为五层闸门，越靠后的层越贵、越接近真机：

| 层 | 命令 | 拦住什么 | 耗时 |
|---|---|---|---|
| 1. 语言层 | `dotnet build AIFramework.Pure.sln`（0 警告 0 错误） | 语法/类型/nullable/analyzer 规则（AIF001~004） | 秒级 |
| 2. 纯逻辑测试 | `dotnet test AIFramework.Pure.sln` | 切片与内核行为、架构拓扑（ArchTests）、0 分配基线 | 秒级 |
| 3. 生成物一致性 | `dotnet run --project tools/viewgen -- --all` | 手改 `.g.cs`、改了 bindings 忘重新生成 | 秒级 |
| 4. 适配层形状 | `pwsh unity/tools/check-adapter-compile.ps1` | Unity 适配层与编辑器脚本的语法/类型/接口实现错误（用形状桩，**不需要 Unity**） | 秒级 |
| 5. 真 Unity | `pwsh unity/tools/generate-scenes.ps1`（场景生成 + 装配校验）<br>`pwsh unity/tools/run-unity-tests.ps1 -TestPlatform EditMode`<br>`pwsh unity/tools/run-unity-tests.ps1 -TestPlatform PlayMode` | 序列化引用漏注入、Build Settings 顺序、StreamingAssets 表加载、真实物理碰撞链路 | 分钟级 |

**已知边界（必须诚实记录）**：
- 第 4 层用形状桩编译，**发现不了"Unity 包里没有这个 API/没有装这个 package"**（真实案例：`UnityEngine.UI` 属 `com.unity.ugui` 包，桩里有、真 Unity 里缺包直接编译失败）。
- 第 5 层通过"临时副本工程 + batchmode"实现：同一 Unity 工程同时只能被一个进程打开，用户开着编辑器时对 `unity/` 直接跑 batchmode 会被 abort。副本保留 `Library` 做增量导入，并用 `robocopy /MIR` 保证删掉的文件不会残留在副本里（否则会出现"仓库已删、副本还在"的重复类型错误）。
- 未覆盖：渲染观感、UI 布局、手感、动画时序——这些只能人眼验收。

## 七、 核心术语对照表

| 标准术语 | 英文 / 代码对应 | 禁混淆别名 | 简明释义 |
|---|---|---|---|
| **边界契约卡** | `CONTRACT.md` | 模块说明文档 | 每个切片根目录下的精简契约说明书（限 60 行内），写明输入输出 CQE、子表、禁区与验收命令。 |
| **Roslyn 编译守卫** | `AIFramework.Analyzer` | 人工 Code Review | 基于 `netstandard2.0` 的编译器诊断插件，在编译期直接将跨切片命名空间引用与引擎泄漏报为 Error。 |
| **架构依赖守卫** | `AIFramework.ArchTests` | 代码规范检查 | 在单元测试阶段运行的代码依赖拓扑与 Analyzer 负向校验，防止绕过编译规则。 |
| **切片脚手架** | `Slice Scaffolding` | 手动新建文件夹 | 自动生成标准切片目录、命名空间模板、契约卡与测试壳的命令行脚本。 |
| **模拟时间源** | `ITimeProvider` / `MockTimeProvider` | `DateTime.Now` | 抽象后的时间接口，真机取系统/服务器时间，测试时可由用例自由快进跨天逻辑。 |
| **双边特例隔离区** | `Interactions/` | 跨模块补丁 | 专门收口极少数无法通过通用 CQE 或 Tag 表达的两两专属交互规则的独立白名单区。 |
